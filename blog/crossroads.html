Crossroads:

Where did the tokens go, and why did the agent fail?

Author

Paul Trust

Published

August 2026

Code

TL;DR

A benchmark reports whether an agent passed. It says nothing about where the tokens went, which steps were wasted, or why the run failed, and real sessions are messier than benchmark runs.

Crossroads turns a raw agent transcript into a sequence of decisions and builds views on top of it: token economics, compaction, failure patterns, behaviour audits and concrete fixes. Signals that come straight from the trace are exact and free; an optional LLM judge adds explanations that are always linked back to the steps they describe.

On five software engineering runs with a pass rate of one in five, Crossroads shows that three of the four failures were loops with three different causes, and pinpoints where each loop began.

Real agent sessions rarely look like a benchmark run that ends with passing tests. A user asks several questions in one session, interrupts, changes direction, and the agent succeeds on one task and fails on the next. Tokens cost money, so it matters where they went. And as agents are given more autonomy, passing the tests is not enough: it also matters whether the agent did what was asked and avoided destructive actions.

Answering these questions today means reading thousands of lines of transcript by hand. Crossroads is built to answer them from the transcript alone.

From transcripts to decisions

Every view rests on one data model. Each session is normalised into a flat list of steps, where a step is one agent decision: a tool call paired with the observation it returned. Steps are grouped by the user request that triggered them, and long sessions are split into segments where the task changes, using textual similarity between requests.

Trace signals

What can be learned without any model?

  • Token economics. Per step accounting of input, cached and output tokens, cache dynamics, and the cost of cache invalidation events, where the reusable prefix of the context collapses and must be paid for again.
  • Compaction. What changed when the context was compacted, and how many tokens were spent afterwards recovering what was lost, for example by reading the same files again.
  • Failure signals. Tool errors, retries, failed tests and repeated actions, combined into heuristic failure modes such as a loop with no progress.
  • Files and topics. Which files were read, edited and tested, and how the agent's thoughts and the user's requests cluster by topic.

Judge analysis

What needs a model, and how is it kept honest?

Some questions, such as why a run failed or whether a behaviour was unsafe, need judgement. Crossroads uses an LLM judge[1] to label the failure pattern of a session, whether it was recoverable, and any unusual or unsafe actions. Judge outputs are shown separately from trace signals and always linked to the steps they refer to, so a reader can check a verdict rather than take it on trust.

Actions

How does analysis turn into a fix?

Patterns that recur across sessions, such as the same instruction repeated by the user or the same files read again and again, are turned into concrete suggestions: project rules, hooks and prompt changes that would prevent the pattern in later sessions.

Related work

Visual analysis of agents. AgentLens[2] builds hierarchical temporal summaries of agent behaviour in LLM based multi agent simulations and traces causes between behaviours. AgentDiagnose[3] scores trajectories on five agentic competencies, such as backtracking and self verification, and visualises them with embeddings and timelines. SeaView[4] supports inspecting and comparing software engineering agent experiments. Crossroads differs in its unit of analysis and its questions: it treats every tool call as a decision, compares many real sessions at once, and puts cost, cache use and compaction next to failure.

Where tokens go. Empirical studies of token use in agentic software engineering[5] and of token economics for agents more broadly[6] quantify how spend is distributed across phases and tools. Crossroads makes the same kind of accounting interactive and per step, so the cost of a particular wasted read or cache invalidation can be found in the trace.

Exploring topics. The topic views follow the embed, cluster, label and project pipeline used to explore concepts inside language models[7], applied here to agent thoughts and user requests.

Case study

Case study 1

What does a pass rate of one in five hide?

Figure 1 applies Crossroads to five software engineering runs across five repositories, each produced by a different agent configuration, with about one million tokens in total. Only one run resolved its task.

  • The failures share a shape but not a cause. The heuristic detector flagged three of the four failed runs as loops, where the agent repeats an action without progress. The judge assigned them three different causes: a knowledge gap, an execution error and a planning error. Each calls for a different fix.
  • The loop is located, not just detected. In one run the agent entered a loop at step 17, making six edits in 32 steps, and the verdict points to the step where the repetition began.
  • Cost and outcome are decoupled. The most expensive run used about six times the tokens of the cheapest, and both failed. In the run that truncated long observations, truncation cut served observation tokens by 28%, visible step by step in the trace.

A single pass rate would hide all of this. The value of the views lies in separating runs that failed for different reasons and in showing where each budget went.
